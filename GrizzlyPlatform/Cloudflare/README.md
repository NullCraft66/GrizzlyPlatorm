# GrizzlyPlatform on Cloudflare

This is the selected target architecture: a standalone Blazor WebAssembly UI served as static Worker assets, with the API on the same Cloudflare origin and D1 as the durable database.

## Current status

- The existing Blazor pages are converted in place to standalone WebAssembly; the original UI project remains the source of those pages. Cloudflare serves the static bundle and `/api/*` from the same origin.
- The Worker serves static assets and routes `/api/*` requests to itself before static-file handling. Hosted device pairing now advertises the current HTTPS origin rather than a computer's LAN/mDNS address. Nexus settings, registered-event lookup, live event status, pit addresses/map, and the combined snapshot have Worker routes. Nexus settings are administrator-only, and the Nexus API key is stored encrypted in D1 with AES-GCM; the encryption key is a required Cloudflare secret and is never stored in D1.
- D1 season/event and team CRUD, event-roster read/add/remove (including Nexus event-key updates), active device configuration reads/writes, and Game Forms form/field/option authoring are implemented against the ASP.NET response contracts. Manual event-roster changes pause automatic TBA roster replacement. Form creation retains required Pit/Match system fields; those fields cannot be edited or deleted, and existing option IDs survive field edits. Match reads and full create/update/delete routes preserve event-roster validation, duplicate checks, optimistic revisions, and protection of matches with scouting submissions. Scouting submission creation (both the legacy model route and current scout route), review/list and detail reads, event reads, answer edits, and administrator-only clearing are implemented. Submission creation keeps the existing form/team/event/match/required-answer and duplicate checks for the current scout workflow. Event Operations supports queued TBA sync plus manual roster, ranking, and match edits with revision checks; the existing read-only Blue Alliance team and match preview routes are also available. Alliance Planning supports the shared versioned plan, ordered wishlist, device suggestions, idempotent retries, and host review. Alliance Selection now supports event reads, start, pick, decline, undo, and delete, with its captain/ranking snapshot and pick history stored in D1. Other API routes still return `503 backend_migration_incomplete`; this remains a migration in progress, not a student-ready release.
- The Blue Alliance teams, matches, and rankings synchronization runs through a Cloudflare Queue, with a dead-letter queue for retry exhaustion. Sync state is persisted in D1 and the existing Event Operations screen polls it; source data is validated before writes and a bad or incomplete response keeps the existing saved data. TBA responses use their ETag/If-None-Match support. `TBA_API_KEY` is declared as a required Worker secret so Wrangler loads it from local `.dev.vars` and validates it before deployment.
- Login verifies the existing ASP.NET Identity V2/V3 PBKDF2 hash formats, then issues a 12-hour `Secure`, `HttpOnly`, `SameSite=Lax` session cookie. D1 stores only the SHA-256 digest of each random session token. The browser restores its login from `/api/auth/me`; logout revokes the server-side session.
- Login attempts are rate-limited by normalized username using a Cloudflare Rate Limiting binding (10 attempts per 60 seconds); the username is hashed before it becomes a binding key. Login fails closed with `503` if that binding is missing or unavailable. Cloudflare documents these counters as approximate and local to each Cloudflare location, so this is a defense-in-depth throttle, not a globally exact account lockout. The namespace ID in `wrangler.jsonc` must be replaced with one unique to the Cloudflare account before deployment.
- Nexus webhook-driven student notifications are not wired yet. Nexus can push event status to a Worker webhook, but recipients and delivery (in-app, browser push, or email) still need to be defined before creating a notification pipeline. The current Nexus routes provide authenticated live reads and the existing settings/test-connection flow.
- Same-origin `GET /api/events` and `GET /api/seasons` are public for the existing guest home/events pages. Other implemented data reads and the user list require a valid server session; listing users requires the `Admin` role or an existing trusted staff account. Mutating API requests are rejected unless their `Origin` matches the Worker origin.
- API readiness intentionally remains degraded until production D1 setup, imported users/application data, the account-specific rate-limit namespace, and end-to-end checks are complete. Do not deploy this Worker for student use yet.

## Local development

Install JavaScript tooling from this directory with `npm install`. `npm run typecheck` checks the Worker code; `npm test` runs API contract tests against mocked D1 plus Worker tests using a SQLite-backed D1 adapter and the checked-in migrations. Apply the checked-in schema to Wrangler's local D1 database with `npm run db:migrate:local`. Wrangler locally simulates the configured Queues. For local development, copy `.dev.vars.example` to the ignored `.dev.vars` file and replace both values. Generate the Nexus encryption value with `openssl rand -base64 32`; keep it unchanged across deployments and backups, or previously stored Nexus keys cannot be decrypted. Before using a real Cloudflare account, create a D1 database and replace the placeholder `database_id` in `wrangler.jsonc`; configure both queues and provide both required secrets (`TBA_API_KEY` and `NEXUS_SETTINGS_ENCRYPTION_KEY`) in Cloudflare. Do not apply remote migrations until the production database and data-import plan are reviewed.

`npm run build:web` publishes the standalone WebAssembly UI to the ignored `Cloudflare/dist/wwwroot` folder, and `npm run dev` builds it before starting Wrangler. The Web project emits ordinary .NET assemblies instead of Webcil and disables Blazor's precompressed gzip/Brotli variants because this static-asset host doesn't perform Blazor's compressed-file content negotiation. Cloudflare can still compress supported response types at the edge. The separate ignored output folder also prevents stale compressed files from older publish runs from being uploaded.

The app's full end-to-end flow is not ready yet: unknown API routes still return `503 backend_migration_incomplete`, and protected browser workflows remain untested. Local Wrangler checks have exercised SPA routing, Home and Events, and the login throttle. The new authentication schema does not create or import accounts: existing `Users` rows and password hashes must be migrated into D1 before sign-in can work. Do not deploy for student use until accounts and app data are imported, the account-specific rate-limit namespace is checked, remaining server-side policies are in place, D1 and Queues are provisioned, and end-to-end checks pass.

To exercise the existing C# API during the transition, start these from this directory in separate terminals:

```sh
dotnet run --project ../GrizzlyPlatform.Api/GrizzlyPlatform.Api.csproj --launch-profile http
dotnet run --project ../GrizzlyPlatform.Web/GrizzlyPlatform.Web.csproj --launch-profile http
```

The API profile is `http://localhost:5263` and the WebAssembly development profile is `http://localhost:5019`; the development-only API setting points the browser UI to that local API. This local setup is only for development; the production app will use same-origin `/api` requests. A WebAssembly publish and basic Wrangler/browser smoke checks have been exercised locally; authenticated end-to-end flows and the complete API migration are still outstanding.

No Cloudflare account resources or production secrets are configured by this project yet.
